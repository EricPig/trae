# AI 推荐子系统架构

> **Specialist**：`llm-evaluation`（通过 `architecture-decisions` 路由推导）  
> **Iron Law**：AI 不做推荐计算，只做约束提取 + 证据检索 + 格式化。推荐计算 = 二维准入 + 安全过滤 + 排序（C3 推荐引擎独有）。  
> **核心约束**：两条红线 = 0%（过敏原违反率 + 门店事实幻觉率）+ P95 ≤ 1.2s + 成本受控  
> **来源**：产品全案 §2.3 核心能力三角、§3.9 AI 态度、§5 产品设计方案、§6 数据方案

## 1. AI 推荐 vs 推荐引擎的职责边界

                    │            用户查询/对话                      │
                    └──────────────┬──────────────────────────────┘
                                   │

## 2. 两条红线的 AI 侧实现

### 2.1 过敏原违反率 = 0%

```
用户对话: "我对花生过敏，帮我找成都的本地菜"
                    │
                    ▼
┌──────────────────────────────────┐
│ Layer 1: 约束提取                │
│ 提取: { diet_restriction: 花生 } │
└────────────────────┬─────────────┘
                     │
                     ▼
┌──────────────────────────────────┐
│ Layer 2: 安全硬过滤（召回层）     │
│                                  │
│  约束 → 推荐引擎                 │
│  推荐引擎在召回层过滤:            │
│  ✗ 含花生的菜品 → 直接排除       │
│  ✓ 不含花生的菜品 → 保留         │
│  ? 过敏原信息缺失 → 诚实降级     │
└────────────────────┬─────────────┘
                     │
                     ▼
┌──────────────────────────────────┐
│ Layer 3-4: AI 不能恢复被过滤的条目│
│                                  │
│  推荐引擎输出的候选集            │
│  已经是过滤后的                  │
│  AI 看不到被过滤掉的条目         │
│  AI 没有"恢复"的能力             │
│                                  │
│  若候选集为空:                    │
│  AI 输出: "抱歉，根据您的忌口，  │
│  在成都我们暂时找不到合适的本地菜│
│  推荐 —— 建议您放宽某些限制"    │
└──────────────────────────────────┘
```

**关键设计**：
- 过敏原过滤在**召回层**（候选集形成前），AI 看不到被过滤的条目
- AI 无法绕过过滤（推荐引擎是唯一数据源，且 ACL 阻止 AI 直连 DB）
- 过敏原信息缺失 = 诚实降级，AI 不推测"可能不含花生"

### 2.2 门店事实幻觉率 = 0%

```
AI 输出中所有事实性陈述（门店地址、营业时间、价格、技法描述等）
                    │
                    ▼
          ┌──────────────────┐
          │ 必须来自 PostgreSQL│
          │ （AI 不直连 DB，   │
          │  通过推荐引擎接口） │
          └──────────────────┘
                    │
              ┌─────┴─────┐
              ▼           ▼
         ✅ 有数据源      ❌ 无数据源
              │           │
              ▼           ▼
         正常输出      诚实降级
         + 来源标注    + 标注"资料不足"
```

**关键设计**：
- AI 回答中所有事实内容必须经过 RAG 检索，且有数据源引用
- LLM 只做格式化，不生成新事实（静态代码检查保证：LLM 输出模板中不含新内容生成指令）
- 运行时审计：每日抽查 AI 推荐结果，验证每个事实陈述都有 PostgreSQL 源头

## 3. AI 评估框架（Evaluation）

### 3.1 评估维度

| 维度 | 指标 | 阈值 | 评估方式 | 周期 |
|------|------|------|---------|------|
| **诚实性** | 不确定时承认率 | ≥ 95%（不确定时不编造） | 测试集（覆盖 E1–E14 所有异常场景）+ Gate 5 理解度 | 每次 AI 发布 |
| **红线防护** | 过敏原违反率 | **= 0%** | 自动化测试（所有过敏原 × 所有菜品 × 所有画像组合）| pre-commit + 每日 |
| **红线防护** | 门店事实幻觉率 | **= 0%** | RAG 覆盖率测试 + 运行时审计（每日 100 条）| pre-commit + 每日 |
| **推荐质量** | 推荐 CTR | ≥ 22% | A/B 实验（MDE 5%，T1 启动）| T1 A/B |
| **推荐质量** | 清单锁定率 | ≥ 40% | 行为分析看板 | 每周 |
| **收敛效率** | 对话收敛轮次中位数 | ≤ 4 轮 | 对话日志分析 | 每周 |

| **来源标注** | 来源标注率 | = 100% | 静态检查 + 运行时审计 | 每次数据接入 |
| **能力档位披露** | 披露率 | = 100% | 静态检查 | 每次 AI 发布 |
| **幻觉模式防护** | "善意编造"检测 | 任何编造模式出现即红 | 测试集 + 运行时异常检测 | 持续监控 |

## 4. AI 成本与延迟预算

### 4.1 延迟预算（P95 ≤ 1.2s 总预算）

| 阶段 | 预算 | 实现策略 |
|------|------|---------|
| Layer 1: 约束提取 | ≤ 200ms | LLM 快速模型 + 结果缓存（同约束 5 分钟内复用） |
| Layer 2: 推荐引擎 | ≤ 500ms | Redis 缓存命中优先（≤ 1ms）；MISS 直查 PostgreSQL（≤ 50ms） |
| Layer 3: RAG 检索 | ≤ 200ms | 向量索引预构建 + 缓存 |
| Layer 4: 诚实层 | ≤ 50ms | 规则引擎（非 LLM） |
| Layer 5: 格式化 | ≤ 200ms | LLM 小模型 + 模板约束（减少输出长度） |
| **总计** | **≤ 1.15s** | 留 50ms 网络开销余量 |

**降级策略**：
- Layer 1/5 LLM 不可用 → 降级为直接推荐（跳过 AI 对话，复用推荐引擎）
- Layer 3 RAG 不可用 → 降级为结构化搜索（从 PostgreSQL 直接读）
- Layer 2 推荐引擎缓存 MISS → 直查 DB（延迟从 1ms 升到 50ms，可接受）

### 4.2 成本预算

| 阶段 | 成本 | 策略 |
|------|------|------|
| Layer 1 约束提取 | 中 | 快速小模型 + 强缓存 |
| Layer 5 格式化 | 低 | 模板约束 + 最小输出长度 |
| RAG 存储 | 低 | 开源向量库自托管（非 SaaS）|
| **核心原则** | **AI 只做"理解"和"格式化"，推荐计算用确定性算法** | 推荐引擎计算 = 零额外 LLM 成本 |

**缓存策略**：
```
约束提取缓存:
  key = hash(用户查询) 
  value = StructuredConstraint JSON
  TTL = 5 分钟
  命中率目标: ≥ 60%

推荐结果缓存:
  key = hash(StructuredConstraint) + locality_filter
  value = 候选列表 + 判定结果
  TTL = 10 分钟
  命中率目标: ≥ 70%

RAG 检索缓存:
  key = hash(candidate_id)
  value = 证据链 JSON
  TTL = 数据不变更则永久
  命中率目标: ≥ 95%
```

## 5. AI 服务降级矩阵

| 组件 | 故障 | 降级行为 | 用户看到的 | 影响 |
|------|------|---------|-----------|------|
| LLM 服务不可用 | 超时 > 5s | 跳过 AI 对话，直接返回推荐 | "AI 暂时不可用，正在为您直接筛选推荐" | 对话功能失效，但推荐正常 |
| RAG 检索不可用 | 向量库故障 | 从 PostgreSQL 直接读证据链 | 证据链内容一样，但格式稍差 | 用户感知不明显 |
| 推荐引擎不可用 | Redis + PostgreSQL 同时故障 | 全站降级 | "服务暂时不可用" | 严重故障，但概率极低 |
| 向量索引过期 | 定期重建失败 | 回退到 PostgreSQL 直接读 | 同上 | 用户感知不明显 |
| 数据源缺失 | ETL 失败 | 诚实降级话术自动触发 | "部分信息可能未及时更新" | 预期内行为 |

## 6. Anti-Corruption Layer（ACL）设计

> **这是 AI 子系统最重要的架构决策**。AI 不直接操作 PostgreSQL，通过推荐引擎接口获取数据。这是防止 LLM 幻觉污染数据源的关键防线。

```
┌──────────────┐     ACL      ┌──────────────┐
│   AI 推荐    │─────────────→│  推荐引擎    │
│              │  (唯一通道)   │              │
└──────┬───────┘              └──────┬───────┘
       │                              │
       │ ❌ 禁止直连                   │ ✅ 内部依赖
       │                              │
       ▼                              ▼
  PostgreSQL                    PostgreSQL
  (AI 无权访问)                 (推荐引擎有权访问)
```

**ACL 三层保障**：
1. **架构层**：AI 服务进程不配置 PostgreSQL 连接池 → 物理上不能直连
2. **代码层**：静态扫描检查 AI 模块中不得出现数据库客户端库的 import
3. **测试层**：集成测试模拟推荐引擎接口故障 → AI 必须能降级，不得绕过

## 7. AI 诚实性的架构级实现总结

| 诚实性承诺 | 架构实现 | 适应度函数 |
|-----------|---------|-----------|
| "不知道就说不知道" | Layer 4 诚实层 + 数据源缺失检测 | FF-SAFE-02（幻觉率 = 0%） |
| "不编造事实" | ACL + RAG 强制检索 + LLM 只做格式化 | FF-SAFE-02 + FF-ARCH-04 |
| "推荐必附依据" | Layer 3 RAG 证据链 + 格式化输出 | FF-DATA-01（来源标注率 = 100%） |
| "明确能力边界" | Layer 4 能力档位声明 | 静态检查（AI 输出模板必须含声明）|
| "商业导流透明" | Layer 4 透明声明 + "不看推广"开关 | FF-ARCH-03（推荐/导流物理隔离）|
| "绝对安全" | Layer 2 召回层硬过滤 + ACL 阻止 AI 绕过 | FF-SAFE-01（过敏原违反率 = 0%）|
