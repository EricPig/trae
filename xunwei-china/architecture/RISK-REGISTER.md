# 风险登记册

> **Iron Law**：每个风险必须有 likelihood、impact、mitigation、owner 和 trigger。模糊的"可能有风险"条目不合格。  
> **来源**：产品全案 §8 风险登记册、基线清单各裁决中的"不决策的后果"  
> **评估标准**：Likelihood（1–5 极低→极高）× Impact（1–5 极低→极高）= 总分（≥8 为 Critical，≥4 为 High）

## Critical 风险详表

### R01 · 过敏原违反红线

| 字段 | 值 |
|------|-----|
| **描述** | 有明确忌口/过敏的用户，推荐结果中出现对应过敏原 → 真实健康损害 |
| **Likelihood** | 2（低，但非零 —— 数据源缺失 + AI 绕过过滤两条路径）|
| **Impact** | 5（致命级 —— 产品定位的杀手级差异化消失 + 法律风险 + 用户信任不可逆损失）|
| **触发条件** | ① 召回层过滤逻辑 bug；② AI 通过 ACL 绕过；③ 数据源缺失导致过滤失效；④ 新过敏原类型未覆盖 |
| **Mitigation** | 
| | - 静态代码检查：过敏原过滤链路完整性编译期验证（pre-commit）|
| | - 自动化测试：所有过敏原类型 × 所有菜品 × 所有画像组合 |
| | - Gate 5 独立门禁：R4 被试理解度 ≥80%（不依赖 63 天 AB）|
| | - 运行时监控：每日自动扫描推荐结果 |
| | - 架构防线：过敏原告在**召回层**（候选集形成前），AI 看不到被过滤的条目 |
| | - 数据源缺失 = 诚实降级，不推测 |
| **适应度函数** | FF-SAFE-01（过敏原违反率 = 0%）|
| **Owner** | 架构师 + AI 团队 |
| **Status** | Active（架构层已防御，等待 T0 Gate 5 验证）|

### R02 · AI 善意编造

| 字段 | 值 |
|------|-----|
| **描述** | AI 在数据源缺失时编造门店事实、菜品描述、营业时间等 → 用户信任崩塌 |
| **Likelihood** | 3（中等 —— LLM 天生倾向补全缺失，尤其是在用户持续追问时）|
| **Impact** | 5（致命级 —— 产品定位是"可核验的裁决"，编造 = 核心叙事崩塌 + 竞争对手可利用）|
| **触发条件** | ① LLM 未被强制 RAG 检索；② AI 绕过推荐引擎直连 DB；③ 格式化层混入事实生成指令；④ 数据源覆盖不足时 LLM 被迫补全 |
| **Mitigation** |
| | - ACL：AI 不直连 PostgreSQL，只通过推荐引擎接口获取数据 |
| | - RAG 强制：所有 AI 输出中的事实性陈述必须有检索结果 |
| | - 诚实层：数据源缺失 → "资料不足"而非补全 |
| | - 静态检查：LLM 输出模板中不含事实生成指令 |
| | - 运行时审计：每日 100 条 AI 推荐抽查 |
| | - E14 场景覆盖：用户问"隐藏款"→ AI 诚实说无，不推荐相似店冒充 |
| **适应度函数** | FF-SAFE-02（幻觉率 = 0%）+ FF-ARCH-04（AI 不生成菜品描述）|
| **Owner** | AI 团队 |
| **Status** | Active（ACL 已设计，等待 pre-commit 脚本实现）|

### R03 · 开源数据许可证合规

| 字段 | 值 |
|------|-----|
| **描述** | 首批 5 省数据依赖的开源/公开数据源许可证不允许商业使用或有 ODbL 覆盖问题 |
| **Likelihood** | 3（中等 —— 部分数据源许可证含糊，需法务逐条审计）|
| **Impact** | 4（高 —— 数据源不可用 → 冷启动受阻；若上线后才发现 → 需下架全部依赖该数据源的内容）|
| **触发条件** | ① T0 W4 之前 E7 影子实验未启动；② 许可证审计遗漏 ODbL 兼容要求；③ 数据源商用禁令未识别 |
| **Mitigation** |
| | - T0 W1 铁律：不自建数据采集（避免陷入"先采后审"的陷阱）|
| | - Gate 4 必须第一个跑：数据可得性盘点 + 许可证审计 |
| | - 法务启动（硬日期 2026-10-05，T0 W1 周一）|
| | - ODbL 法律构造双路径：开放版本 + 商业合同叠加 |
| **适应度函数** | FF-DATA-03（数据版本追溯 = 100%）|
| **Owner** | 数据团队 + 法务 |
| **Status** | Active（法务待启动，硬日期已锁定）|

### R04 · 🔴 条目占比被误读为失败

| 字段 | 值 |
|------|-----|
| **描述** | 数据团队或管理层看到 🔴 占比高，推动"优化"（压制隐藏款条目）→ 亲手摧毁差异化护城河 |
| **Likelihood** | 4（高 —— 人天然倾向降低"红色占比"，基线清单已识别为"指标反噬"）|
| **Impact** | 4（高 —— 架构层已设计保护，但若决策层误判，会从产品定义层推翻差异化）|
| **触发条件** | ① 主看板单独呈现 🔴 占比单值；② 决策层问"为什么红色这么多"且无人引用指标反噬框架 |
| **Mitigation** |
| | - 主看板**不单独呈现** 🔴 占比单值，只呈现二维矩阵 |
| | - 「🔴+高本地性曝光份额」设为**只升不降**护栏指标 |
| | - 任何"优化 🔴 占比"的提案必须回答 3 个必答问题（不答即驳回）|
| | - 产品全案 §1.6 指标反噬风险已写死，作为全员必读 |
| **适应度函数** | FF-GUARD-01（🔴+高本地性曝光份额只升不降）+ FF-GUARD-02（不单独优化 WDCU）|
| **Owner** | 数据团队 + PM |
| **Status** | Active（护栏已设计，看板需确保实施）|

## High 风险详表

### R05 · 二维准入表参数漂移

| 字段 | 值 |
|------|-----|
| **描述** | 开发者修改准入表参数（阈值从 60 改成 55）但忘记同步修改其他层的约束或文档 |
| **Likelihood** | 2（低 —— 但参数表有 4 行 × 阈值，漏改一行会导致局部准入异常）|
| **Impact** | 4（高 —— 参数漂移是基线清单反复出现的问题：92/95 年临界点、59/68.2 对账、50/35/15 vs 60/25/15）|
| **Mitigation** |
| | - 回归断言 R1–R5 全部挂 pre-commit + CI |
| | - 修改准入表参数必须跑 `data_metrics_calc_exp.py` 验证准入率 + 交叉反转率 |
| | - 所有参数集中在单一配置文件（不分散在各处）|
| **适应度函数** | FF-ADJ-01 + FF-ADJ-02 + FF-SCR-03 |
| **Owner** | 架构师 |
| **Status** | Active（脚本已就绪，需确保 pre-commit hook 覆盖）|

### R06 · LLM 成本超预算

| 字段 | 值 |
|------|-----|
| **描述** | AI 对话量超出预期，LLM token 成本吞噬 T1 预算 |
| **Likelihood** | 3（中等 —— AI 对话是 T1 新功能，真实使用量未知）|
| **Impact** | 3（中等 —— 有降级路径，但会影响用户体验）|
| **Mitigation** |
| | - AI 只做约束提取 + 格式化（不做推荐计算），推荐引擎 = 零 LLM 成本 |
| | - 强缓存策略（约束提取 TTL 5 分钟 + 推荐结果 TTL 10 分钟）|
| | - LLM 选择：快速小模型用于约束提取，大模型仅用于 R4 高危场景 |
| | - 预算上限：每月 LLM 成本设硬上限，超支自动降级 |
| **适应度函数** | 成本看板（LLM cost / month）|
| **Owner** | AI 团队 + Finance |
| **Status** | Active（预算已锁定，缓存策略已设计）|

### R07 · 用户画像数据隐私泄露

| 字段 | 值 |
|------|-----|
| **描述** | 用户忌口/过敏数据被未授权访问或外泄 → 合规风险 + 用户信任损失 |
| **Likelihood** | 1（极低 —— 但影响极端）|
| **Impact** | 5（致命级）|
| **Mitigation** |
| | - 忌口/过敏数据默认本地存储（不上传到服务器，除非用户显式授权）|
| | - 服务器端存储的画像数据加密（AES-256）|
| | 一键清除所有画像数据（合规要求）|
| | 服务端严格访问控制（画像服务仅推荐引擎 + AI 推荐可访问，且为只读）|
| | 不收集未成年人画像（技术拦截）|
| **Owner** | 安全团队 |
| **Status** | Active（隐私设计已纳入需求，等待架构评审）|

### R08 · 推荐延迟超标

| 字段 | 值 |
|------|-----|
| **描述** | 推荐接口 P95 > 1.2s，用户体验恶化 |
| **Likelihood** | 3（中等 —— Redis 缓存 MISS + PostgreSQL 慢查询 + AI 叠加）|
| **Impact** | 3（中等 —— 延迟高会降低留存，但不致命）|
| **Mitigation** |
| | - 缓存优先（Redis 命中率目标 ≥ 70%）|
| | - PostgreSQL 查询优化（索引 + 查询超时 500ms）|
| | - LLM 降级路径（超 200ms 自动切小模型或跳过）|
| | - 监控 + 自动降级（P95 > 2.0s 持续 10 分钟 → 自动旁路缓存）|
| **适应度函数** | FF-PERF-01（推荐 P95 ≤ 1.2s）|
| **Owner** | SRE + 架构师 |
| **Status** | Active（监控已设计，降级路径待实现）|

## 风险依赖关系

```
R01（过敏原红线）
  └─ 依赖 R03（数据源可用）
  └─ 依赖 R05（参数正确）
  
R02（AI 编造）
  └─ 依赖 R03（数据源可用）
  └─ 依赖 ACL 不被绕过

R04（指标反噬）── 独立风险，但需要 R05（参数正确）才能正确理解指标

R03（数据合规）
  └─ 硬日期 2026-10-05（T0 W1 周一）
  └─ Gate 4 第一个跑

R08（延迟）
  └─ 依赖 R06（LLM 成本控制）→ 预算不够就没法上缓存
```

## 风险响应策略总表

| 策略 | 适用风险 | 说明 |
|------|---------|------|
| **避免（Avoid）** | R01, R02 | 架构层设计使红线不可能被违反（召回层过滤 + ACL）|
| **缓解（Mitigate）** | R03, R04, R05, R06, R08 | 多道防线 + 监控 + 自动降级 |
| **转移（Transfer）** | R07 | 加密 + 访问控制 + 合规审计 |
| **接受（Accept）** | R09（数据源缺失）| 诚实降级是产品设计的一部分，不是 bug |
| **保留（Retain）** | R10, R12, R15 | 中等概率 + 中等影响，有应对预案即可 |

## 每月风险回顾 Checklist

- [ ] Critical 风险的 mitigation 措施是否已落地？
- [ ] 适应度函数测试脚本是否覆盖了所有 Critical 风险？
- [ ] 硬日期（2026-10-05 法务启动）是否已执行？
- [ ] 数据源覆盖度是否在提升？（R09 数据源缺失 → 诚实降级过度）
- [ ] 🔴+高本地性曝光份额是否在上升？（R04 护栏）
- [ ] LLM 成本是否在预算内？（R06）
- [ ] 用户反馈中是否有任何"编造"或"推荐不准"的投诉？（R01 + R02 早期信号）
- [ ] 二维准入表参数是否最近被修改过？修改是否验证过？（R05）
